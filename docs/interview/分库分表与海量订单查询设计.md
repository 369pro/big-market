# 分库分表与海量订单查询设计

整理日期：2026-09-30。

本文整理本次对话中的分库分表方案、项目 ES 查询定位、侧边栏追问，以及“每天 500 万订单”的面试场景题。项目已实现的能力与面试设计建议分别说明，不将建议视为项目现状。

## 一、后端数据库常用的分库分表方案

### 1. 按拆分方式分类

| 方案 | 做法 | 主要解决的问题 |
| --- | --- | --- |
| 垂直分库 | 按业务拆库，如用户库、订单库、商品库 | 业务解耦、资源隔离 |
| 垂直分表 | 按字段拆表，如商品基本信息与商品详情 | 减少大字段对常用查询的影响 |
| 水平分库 | 同结构的数据分散到多个数据库实例 | 单实例容量、连接数和读写压力 |
| 水平分表 | 同结构的数据分散到多张表 | 单表规模和索引维护压力 |

注意：同一个数据库实例内分表，并没有增加实例的 CPU、内存或磁盘吞吐，不能从根本上解决实例资源瓶颈。将数据放入同一实例的不同逻辑库，也不等于实现物理资源隔离。

### 2. 水平拆分的常用路由规则

| 规则 | 示例 | 优点 | 局限 |
| --- | --- | --- | --- |
| 哈希取模 | `hash(userId) % N` | 数据通常较均匀，等值查询定位方便 | 改变分片数通常需要迁移；范围查询可能跨分片 |
| 范围分片 | 按订单 ID 区间划分 | 范围查询方便，可新增区间 | 可能产生热点和数据倾斜 |
| 时间分片 | 按月、季度组织订单数据 | 方便时间查询、归档和清理 | 当前时间段承受主要写入压力 |
| 映射表路由 | 保存“租户或订单 → 分片”的映射 | 路由灵活，便于单独迁移 | 需要维护映射的可用性和一致性 |
| 一致性哈希 | 通过哈希环定位分片 | 扩缩容时可减少受影响的数据 | 实现与迁移管理较复杂，并非无需迁移 |

实际可以组合使用，例如按用户分库，再按时间分表，但应评估组合后路由与查询的复杂度。

### 3. 分片键如何选择

原则：优先让高频查询可以直接定位分片，同时兼顾数据均匀性、热点和扩容成本。

- 用户查询自己的订单较多：考虑 `userId`。
- 主要按订单号查询：考虑 `orderId`，或让订单号携带可解析的路由信息。
- 多租户场景：考虑 `tenantId`，但要处理大租户倾斜。
- 时间范围查询和归档较多：考虑时间分片，但跨时间查询仍可能访问多个分片。

分片键选择不合适时，一次查询可能变成所有分片都查询一次，再汇总、排序和分页。

## 二、大营销项目中的 ES 查询到底解决什么问题

### 1. 项目背景

根据项目架构说明，用户侧业务数据按 `userId` 路由，采用 2 个库 × 4 张表的水平拆分。用户带着自己的 `userId` 查询，可以定位对应分片。

运营端则可能需要跨用户查看订单，或者只知道订单号、不知道用户 ID。这类查询不能直接依靠 `userId` 路由，因此项目提供独立的 ES 查询侧。

### 2. 对话提问：项目里的 ES 查询主要解决运营人员按订单号查询吗？

结论：面向运营端是对的，但当前代码并没有实现按订单号筛选。

代码证据：

- `big-market-trigger/src/main/java/com/pro/trigger/http/ErpOperateController.java`：`queryUserRaffleOrder()` 的注释为“查询运营数据，用户抽奖单列表”，方法不接收订单号等查询参数。
- `big-market-infrastructure/src/main/java/com/pro/infrastructure/adapter/repository/ESUserRaffleOrderRepository.java`：调用 ES DAO 获取列表并转换返回对象。
- `big-market-app/src/main/resources/mybatis/mapper/elasticsearch/user_raffle_order_mapper.xml`：查询统一索引，没有订单号过滤条件。
- `docs/dev-ops/canal-adapter/es7/`：配置将各分片抽奖订单映射到 `big_market.user_raffle_order` 索引，并以订单号作为文档标识。

当前查询的核心 SQL：

```sql
select _user_id, _activity_id, _activity_name,
       _strategy_id, _order_id, _order_time, _order_state
from "big_market.user_raffle_order"
order by _update_time
limit 10
```

这里没有 `WHERE` 条件，也没有分页参数。`ORDER BY` 未指定降序，因此不能表述为“查询最新 10 条订单”。

合理的面试表达：

> 项目通过 Canal 将分片订单同步到 ES，为运营端提供跨用户、跨分片的订单列表查询。当前实现的是列表查询，按订单号、时间范围、订单状态筛选属于可以继续扩展的能力。

### 3. 侧边栏追问：那就是运营人员查询所有数据，是吧？

需要区分“查询范围”和“一次返回量”：

- 查询范围：同步到该 ES 索引的各分片抽奖订单，不局限于某个用户。
- 一次返回量：当前代码固定返回最多 10 条，不是一次加载全部订单。
- 功能边界：当前是全局订单列表查询，不是全量订单导出，也还没有实现分页。

“所有数据”在这里指跨分片的订单查询范围，不能理解为整个项目所有业务表的数据，也不能据配置断言线上同步绝无遗漏。

## 三、面试场景：每天 500 万订单，如何设计查询系统

### 1. 题目要求

1. 支持按照订单号查询。
2. 支持按照时间范围查询。
3. 有 50 个可能参与查询的条件。
4. 最近一个月的数据经常被查询。

核心思路：将精确查单、复杂检索、冷热数据管理分别设计，不能靠给 MySQL 增加 50 个索引解决所有问题。

建议架构：MySQL 分库分表保存权威订单数据；CDC 将数据同步到 ES 查询副本；按时间组织索引并管理冷热数据。

这是一套面试设计方案，不代表当前项目已经全部实现。

### 2. 先估算规模并澄清约束

- 每天 500 万订单，30 天约 1.5 亿订单。
- 平均每秒约 58 个新订单，但平均值不能代替峰值流量。
- 订单创建之后还有支付、取消、退款等更新，写入量不能只计算新建订单。
- 需要确认高峰写入量、查询 QPS、订单大小、数据保留年限、查询延迟和一致性要求。
- 存储容量还要考虑索引、副本、日志和容量余量，不能直接用订单条数推导分片数量。

数据量决定容量规划，峰值流量与查询模式决定性能设计。

### 3. 按订单号查：定位 MySQL 分片

订单详情通常要求准确、最新，优先通过订单号定位 MySQL 分片，再利用唯一索引查询。

可选方案：

- 按订单号哈希分片：直接计算路由。
- 按用户 ID 分片：在订单号中设计路由信息，或维护“订单号 → 分片”的映射。

注意事项：

- 雪花 ID 本身不自动解决分片定位，需要明确 ID 与路由的关系。
- 路由方案要考虑扩容后的兼容性，不能修改取模数量后直接按新规则查询历史订单。
- 订单号查询不应默认广播到所有分片。

### 4. 时间范围与 50 个动态条件：独立查询侧

通过 MySQL binlog → CDC（例如 Canal）→ ES，建立订单检索副本。

例如：查询最近 7 天、某个渠道、支付成功、金额超过 500 元、某类商品的订单。

对于大量不固定的组合条件，MySQL 中很难用少量联合索引覆盖全部访问模式；ES 可以针对字段建立检索索引，再组合过滤。

但“有 50 个条件”不意味着一定需要 ES，也不意味着所有字段都必须索引。先明确哪些条件常用、是否涉及关联查询和聚合分析，再选择查询系统。

设计约束：

- 区分精确匹配、数值或时间范围过滤、全文检索，按语义设计字段。
- 只索引确实需要检索的字段，避免无节制复制大字段。
- 默认限制时间范围和单次返回量，控制宽泛查询。
- 列表采用游标分页；需要稳定翻页时还应考虑一致的查询视图和稳定排序。
- 大范围导出、重型统计使用异步任务或独立分析链路，避免拖慢在线查询。
- ES 返回列表或订单 ID；用户打开详情、需要最新状态时再查 MySQL，不必对列表每行都无条件回源。

### 5. 最近一个月频繁查询：时间组织与冷热分层

| 数据范围 | 处理方式 |
| --- | --- |
| 最近 30 天 | 作为热数据，放在性能较好的存储层，承担主要查询 |
| 更早的订单 | 转入成本较低的存储层，允许更高查询延迟 |
| 超过保留期限 | 根据业务、合规及审计要求归档或删除 |

ES 可以按天、按月或其他大小策略组织索引，粒度由实际数据大小和压测确定。“一天一个索引”不等于“一天一个分片”。

根据时间范围限定访问的索引，页面默认查询近一个月。时间字段含义必须明确：按创建时间组织索引时，不能简单根据更新时间过滤条件排除旧索引，否则可能漏掉近期发生更新的历史订单。

MySQL 的历史订单也需要归档规划，否则只有 ES 做分层，业务库仍然无限增长。历史订单更新时，还需要能定位原索引，避免产生跨索引重复记录。

### 6. 一致性和故障处理

| 问题 | 设计思路 |
| --- | --- |
| 同步延迟 | 刚下单立即查询、支付状态确认走 MySQL；运营列表接受约定范围内的延迟 |
| 重复同步 | 使用稳定且全局唯一的订单标识作为文档 ID，同一订单写入同一目标索引 |
| 更新乱序 | 使用可比较的订单版本，并在写入时执行版本校验，避免旧状态覆盖新状态 |
| 同步失败 | 重试、异常记录、积压监控、对账和补数 |
| 删除与归档 | 同步处理删除或状态变更，不能只考虑新增事件 |
| ES 不可用 | 订单号查单继续走 MySQL，复杂查询降级，不把检索流量广播到业务库 |

稳定文档 ID 可以避免重复创建文档，但不能单独解决乱序覆盖问题；版本字段也必须配合实际的条件写入逻辑。

## 四、侧边栏补充：两种分片方案、基因法与订单号编码

本节补充截图中遗漏的方案对比，并给出用于理解的数字示例。以下库表数量、编码格式均为教学设计，不是对当前项目实现的描述。

### 1. 两种方案到底有什么区别？

比较的是“数据如何分片”，而不是“十进制数字编码与二进制位运算谁更好”。订单号编码只是帮助查询找到数据的位置。

| 对比项 | 用户分库 + 按月分表 | 用户哈希分库分表（固定 32 个分片） |
| --- | --- | --- |
| 数据位置 | 用户决定库，订单创建月份决定表 | 用户决定固定的库和表 |
| 同一用户的订单 | 分散在同一个库的不同月份表 | 通常集中在同一个分片 |
| 只凭订单号查单 | 需要得到库路由和月份 | 需要得到分片编号 |
| 查用户全部历史订单 | 需要跨月份表查询、合并 | 路由规则不变且未归档时，通常只查一张表 |
| 按时间归档 | 方便按整张月份表归档 | 一般要在各分片内筛选、搬移或删除历史数据 |
| 数据持续增长 | 新建月份表，历史表不再承接新创建订单，但仍可能更新 | 固定的表持续增长，需另行归档或扩容 |
| 新增写入分布 | 分散到各库的当月表 | 分散到各库的多个固定表 |
| 管理成本 | 月份表越来越多，需预建表、跨月路由和归档管理 | 后期容量扩展、路由兼容和数据迁移复杂 |

### 2. 用户分库 + 按月分表：具体例子、优缺点与适用场景

假设有 4 个逻辑分库，为了方便演算，示例直接用 `userId % 4`；实际可使用稳定哈希并评估数据倾斜。

用户 `1006` 的库编号：

```text
dbNo = 1006 % 4 = 2

2026 年 9 月创建的订单 → db_2.orders_202609
2026 年 10 月创建的订单 → db_2.orders_202610
2026 年 11 月创建的订单 → db_2.orders_202611
```

查询行为：

- 查该用户 9 月订单：访问 `db_2.orders_202609`。
- 查该用户 9—11 月订单：访问该库的 3 张月份表，再合并排序与分页。
- 运营查所有用户 9 月订单：仍然涉及各个库的 9 月表，或者交给 ES 查询侧；按月分表不能消除跨库查询。
- 归档 2026 年 9 月订单：可以按各库对应月份表组织归档，但要处理尚未完成的退款等后续更新。

优点：近期查询范围明确，单个月份的数据规模可估算；按时间归档和生命周期管理方便。

缺点：用户全历史查询跨表；需要按时预建表；当月写入集中到每个库的当月表，单库热点仍要评估；跨月分页和统计更复杂。

适合“近期查询多、历史归档多”的订单场景。例如用户主要查看最近 3 个月订单、运营经常按月查数据、两年前的数据进入历史存储。

### 3. 用户哈希分库分表：固定 32 个分片的具体例子

假设 4 个库，每库 8 张表，总共 32 个分片。将稳定用户哈希映射到 `0—31`：

```text
shardNo = stableHash(userId) & 31
dbNo    = shardNo / 8       （整数除法）
tableNo = shardNo % 8
```

假设用户 `1006` 算出的 `shardNo = 22`：

```text
dbNo    = 22 / 8 = 2
tableNo = 22 % 8 = 6

该用户各月份的新订单 → db_2.orders_6
```

优点：用户维度订单查询通常只访问一个分片；路由固定，用户跨月份查询简单。

缺点：各表随时间持续变大；历史归档需要覆盖所有分片；运营时间范围查询可能涉及全部分片；扩容需要兼容旧路由并迁移数据。大客户或热点用户也可能导致倾斜。

适合用户维度查询占主导、经常查看用户完整订单历史的场景，但仍需要容量和归档策略。

注意：不要直接把 `hash % 4` 和 `hash % 8` 分别作为库号和表号，却以为能覆盖全部 32 种组合。两个取模结果存在关联。先得到统一分片编号，再拆成库号和表号，更容易保证路由覆盖。

### 4. 什么是订单号“基因法”？低 5 位如何定位分片？

这里的“基因”指把用户路由信息嵌入订单号，让按用户查询和按订单号查询落到同一个分片。

32 个分片需要 5 个二进制位，因为 `2^5 = 32`。以下假设 `baseId` 是一个独立生成、全局唯一且位宽足够的整数：

```text
shardNo = stableHash(userId) & 31
orderId = (baseId << 5) | shardNo

查询时：
shardNo = orderId & 31
dbNo    = shardNo / 8
tableNo = shardNo % 8
```

数字例子：

```text
baseId  = 1000
shardNo = 22

orderId = 1000 × 32 + 22 = 32022

解码：32022 & 31 = 22
库号：22 / 8 = 2
表号：22 % 8 = 6
最终访问：db_2.orders_6
```

因为 `baseId << 5` 的低 5 位都是 0，所以这里按位或与加上 `shardNo` 等价。

生产注意事项：

- 必须保证基础 ID 唯一、路由算法稳定，并规划位宽和溢出边界。
- 不能把已经接近 64 位上限的雪花 ID 直接左移 5 位，也不能随意覆盖原 ID 的低位，否则可能溢出或破坏唯一性。
- 低 5 位只支持表示 32 个路由编号；扩容不能简单换成低 6 位解释全部历史订单，需要版本或映射兼容。
- 订单号不是权限凭证，知道订单号也必须经过访问权限校验。

### 5. 按月分表时，订单号如何编码？不用字符串也能路由

按月分表需要得到月份；如果还按用户分库，还需要库路由。可以用固定十进制位数编码，也可以设计二进制位段，二者是编码选择，不是两种不同的分片策略。

为了直观，设计以下教学格式：

```text
订单号 = [6 位年月 YYYYMM][2 位库号][8 位序列号]

月份：202609
库号：02
序号：00001234
订单号：2026090200001234
```

全程用整数计算，不需要字符串截取或正则：

```text
orderId = month × 10^10 + dbNo × 10^8 + sequence

month    = orderId / 10^10             （整数除法）
dbNo     = (orderId / 10^8) % 100      （先整数除法）
sequence = orderId % 10^8

解码结果：202609、2、1234
最终访问：db_2.orders_202609
```

同一月份、同一库中的序列号必须不重复，并且小于 `10^8`；库号必须小于 100。序列号生成还需解决并发、多节点唯一性和故障恢复，不能仅凭这个公式宣称已实现分布式 ID。

这个示例值仍在 JavaScript 安全整数范围内，但更长的订单号或其他 64 位 ID 可能超过其上限。因此接口通常可以统一把订单号作为字符串传输；“路由使用数字运算”不等于“所有订单号都可以安全使用前端 Number 保存”。

### 6. 按月分表和基因法有什么关系？能不能一起使用？

- 按月分表方案：订单号需要提供月份；按用户分库时，还需要库的路由信息。
- 上面的低 5 位方案：只编码固定 32 个分片的位置，没有编码月份，不能原样用于按月分表。
- 如果希望使用二进制编码，可以规划 `[时间信息][唯一性信息][库路由基因]`，从时间信息提取订单创建月份，从路由基因提取库号。
- 也可以使用上一节的十进制格式，或通过订单路由映射表查找位置；不一定必须把全部路由信息嵌入 ID。

关键是：订单放在哪个库、哪张表，只凭订单号查询时，就必须能从订单号或路由映射中恢复这两项信息。创建月份一旦参与路由，不能因订单更新时间改变而随意改变。

### 7. 对每天 500 万订单的题目，怎么选？

“最近一个月常查”与明确的历史归档需求，使“用户分库 + 时间分表”成为值得优先评估的方案，但不是唯一正确答案。

- 如果用户全历史查询最重要：固定用户哈希分片可能更直接，再搭配历史归档。
- 如果近期查询、时间检索和生命周期管理最重要：用户分库 + 按月分表更契合。
- 如果一个月单表仍然太大或写入太集中：可以进一步评估按天分表，或月份内再做哈希子分表；这样订单路由还需包含子分表信息。
- 无论选择哪种，50 个动态组合条件都应单独评估查询侧方案，不能指望分库分表本身解决全部检索需求。

以 30 天 1.5 亿条订单为例，若均匀分到 4 个库且每库每月一张表，每张当月表约 3750 万条。这只是容量估算，不能直接据此判定足够或不足；还要结合行宽、索引、硬件和压测。

## 五、面试总结话术

> 每天 500 万订单，一个月约 1.5 亿条。我会将交易存储和运营检索分开：MySQL 分库分表作为权威数据源，订单号查询通过路由规则直接定位分片；时间范围和大量动态组合条件通过 CDC 同步到 ES 后查询，避免在 MySQL 中堆积大量索引。最近一个月的数据作为热数据，历史数据按时间分层或归档，查询采用游标分页，大范围导出异步处理。同时通过同步重试、版本校验和对账补偿保障查询副本的一致性，强实时订单详情仍然查询 MySQL。具体分片数和索引粒度由容量估算与压测确定。
