# 支付链路与数据一致性：面试讲解稿

分析日期：2026-10-13。依据当前工作区源码（包括已有未提交修改），不是只读历史文档。本次只新增讲解资料与流程图，没有修改业务代码，没有发起真实支付或运行外部服务集成测试。数据库唯一约束依据仓库 SQL，未核验运行环境的迁移状态。

## 1. 先划清业务边界

系统有两条不同的支付链路：

| 链路 | 所在服务 | 扣什么 | 得到什么 | 关联标识 |
|---|---|---|---|---|
| 现金充值 | 相邻 `chatgpt-data` 服务 | 支付宝沙箱支付金额 | 对话钱包余额，再触发营销返利 | 充值 orderId、渠道 transactionId |
| 积分兑换 SKU | 当前 `big-market` 服务 | 营销积分 available_amount | 活动抽奖次数 | requestId → outBusinessNo |

现金充值返利会进入 big-market，但钱包余额、营销积分、抽奖次数是不同的账户。积分兑换不调用支付宝，也不直接给对话钱包充值。当前现金渠道实现是支付宝沙箱，不能表述成已上线真实收单或已支持微信支付。

面试主旨：**局部用数据库事务保证原子性，跨服务用持久化事件推动最终一致；重复请求靠业务幂等收敛，故障靠查单、重投和对账恢复。** 当前尚有库存释放和营销消费完成跟踪的缺口，需要如实区分。

## 2. 现金充值：下单 → 支付确认 → 钱包到账 → 营销返利

![现金支付与一致性流程](/Users/tsy/WorkSpace/LLM-market/big-market/figures/payment-cash-consistency.png)

[可编辑 Mermaid](/Users/tsy/WorkSpace/LLM-market/big-market/figures/payment-cash-consistency.mmd) · [Mermaid 预览](/Users/tsy/WorkSpace/LLM-market/big-market/figures/payment-cash-consistency.md)

1. `create_pay_order` 根据用户身份和商品配置创建充值订单，保存价格、手续费、到账金额快照。重复处理按订单快照到账，不按之后修改的商品价格重算。当前代码会复用符合条件的未支付订单，但这不等价于严格的客户端 requestId 幂等下单。
2. 返回支付宝支付链接。浏览器回跳只是界面导航，不能作为入账凭证。
3. `alipay/notify` 验签，校验 appId、订单、渠道、金额；sellerId 在配置后校验。对支付成功或关闭通知再主动查询渠道。用户查询接口也会校验订单归属并主动核对。
4. **事务 A：确认支付。** 条件更新订单为 `WAIT`（已支付待发货），记录渠道交易信息，同时写 `PAID` outbox。二者一起提交，避免“已确认支付但没有补发货任务”。
5. **事务 B：钱包到账。** 条件更新 `WAIT → COMPLETED`；插入唯一 `balance_grant`（`appId=payment, requestId=orderId`）；按到账金额快照增加钱包；同时写 `DELIVERED` outbox。任何一步异常，整个事务回滚。
6. 同步调用到账方法缩短等待；`PAID` 消费和补货任务调用同一个幂等方法，作为恢复路径。
7. `DELIVERED` 消费调用营销 Dubbo `OPENAI_PAY`，以充值订单号作为外部业务号。营销把返利订单与 task 同事务落库；RPC 成功后充值事件标记 `DONE`，积分/次数再由营销 MQ 消费。

### 状态名称最容易讲错的地方

```text
CREATE：待支付
WAIT：已经支付，等待钱包到账（不是等待用户付款）
COMPLETED：钱包到账完成
CLOSE：本地关闭；可信渠道结果为已支付时仍可恢复到 WAIT
```

两类 outbox 事件语义也不同：

- `PAID / DONE`：这条补发货事件已处理完，并确认订单达到 COMPLETED。
- `DELIVERED / DONE`：营销返利 RPC 已成功受理；不证明营销积分和抽奖次数都已到账。

### 为什么 outbox 能恢复，为什么仍然会重复？

充值 relay 扫描 `PENDING` 和到期的 `SENT`，同步发送 MQ，只有 `SEND_OK` 才标 `SENT`；业务处理成功后消费者标 `DONE`。发送和消费失败都有退避时间。

“发到 broker 后、更新 SENT 前宕机”会重复发送；“钱包到账后、更新 DONE 或 MQ 确认前宕机”会重复消费。设计允许这些重复，由订单状态 CAS、唯一流水及返利业务号去重，不能宣称消息只投递一次。

消费者从数据库加载真实事件和订单，校验消息的事件类型与订单号；不直接相信消息里传入的身份。`markSent` 只更新未 DONE 的事件，避免消费者先完成后被发送器改回 SENT。

证据：[充值 outbox 发送与重投](/Users/tsy/WorkSpace/LLM-market/chatgpt-data/chatgpt-data-app/src/main/java/cn/bugstack/chatgpt/data/mq/PaymentEventOutboxRelay.java:42)、[充值事件消费与 DONE](/Users/tsy/WorkSpace/LLM-market/chatgpt-data/chatgpt-data-app/src/main/java/cn/bugstack/chatgpt/data/mq/PaymentEventRocketMqConsumer.java:84)、[充值事件状态 SQL](/Users/tsy/WorkSpace/LLM-market/chatgpt-data/chatgpt-data-app/src/main/resources/mybatis/mapper/payment_event_outbox_mapper.xml:45)。

## 3. 积分兑换：预占 SKU → 待支付单 → 扣积分 → 异步增加次数

![积分兑换与一致性流程](/Users/tsy/WorkSpace/LLM-market/big-market/figures/payment-credit-consistency.png)

[可编辑 Mermaid](/Users/tsy/WorkSpace/LLM-market/big-market/figures/payment-credit-consistency.mmd) · [Mermaid 预览](/Users/tsy/WorkSpace/LLM-market/big-market/figures/payment-credit-consistency.md)

1. Token 入口解析用户身份。`requestId` 经用户、操作名隔离后生成稳定 `outBusinessNo`。同一笔业务超时重试必须复用 requestId。
2. 先查已有业务订单，存在则校验 SKU 并复用原金额；不存在才检查活动并预占库存。Lua 在一次脚本执行中检查库存、扣减、记录 reservationId；同一业务重试不重复扣库存，同一业务号换 SKU 会被拒绝。
3. **事务 A：** 创建 `wait_pay` 活动商品订单，保存积分价格、总/日/月次数套餐快照。
4. **事务 B：** 按 userId 路由分库，把积分流水、余额扣减和消息 task 放在同一个本地事务里。余额不足、账户关闭或 task 写失败会使这笔扣款事务回滚。
5. 提交之后发送 `credit_adjust_success`。只有 broker 确认后 task 才标 `completed`；发送失败记 `fail`，定时任务重发。
6. 消费者只把负向积分事件当成支付，正向签到/奖励积分不触发兑换发货。找不到活动订单会抛异常，不能静默吞掉。
7. **事务 C：** 条件更新 `wait_pay → completed`，同时增加活动账户额度。更新不是 1 行就不再加次数；重复投递因此不会多发。日/月子账户不存在时此处不会强制创建，而由参与流程初始化，不能简单描述为每次必写三条账户记录。

代码：[积分兑换入口](/Users/tsy/WorkSpace/LLM-market/big-market/big-market-trigger/src/main/java/com/pro/trigger/http/RaffleActivityController.java:824)、[订单复用与库存预占](/Users/tsy/WorkSpace/LLM-market/big-market/big-market-domain/src/main/java/com/pro/domain/activity/service/quota/AbstractRaffleActivityAccountQuota.java:61)、[积分事务与业务幂等](/Users/tsy/WorkSpace/LLM-market/big-market/big-market-infrastructure/src/main/java/com/pro/infrastructure/adapter/repository/CreditRepository.java:93)、[兑换发货事务](/Users/tsy/WorkSpace/LLM-market/big-market/big-market-infrastructure/src/main/java/com/pro/infrastructure/adapter/repository/ActivityRepository.java:304)。

积分并发扣款除了用户锁，还有数据库底线，关键条件可概括为：

```sql
UPDATE user_credit_account
SET available_amount = available_amount + :delta
WHERE user_id = :userId
  AND account_status = 'open'
  AND available_amount + :delta >= 0;
```

这是语义化摘录，`delta` 为负数。检查影响行数，不用“先查询余额再无条件扣减”代替原子条件更新。业务唯一流水与扣款在同一事务，不能只依赖 Redis 锁防重。证据：[积分余额条件更新](/Users/tsy/WorkSpace/LLM-market/big-market/big-market-app/src/main/resources/mybatis/mapper/mysql/user_credit_account_mapper.xml:12)、[活动订单状态 CAS](/Users/tsy/WorkSpace/LLM-market/big-market/big-market-app/src/main/resources/mybatis/mapper/mysql/raffle_activity_order_mapper.xml:47)。

## 4. 异常与一致性：面试重点表

| 故障窗口 | 当前处理与结果 | 要讲清的边界 |
|---|---|---|
| 用户付了钱，回调丢失 | 用户查询及定时任务主动查渠道；确认后进入同一支付确认/到账路径 | 超时或查单失败表示结果未知，不能直接判支付失败 |
| 回调重复、用户查询和回调并发 | 支付状态 CAS；到账事务另有 CAS 和唯一 balance_grant | 锁不是唯一正确性保障，业务唯一键与数据库状态才是底线 |
| 渠道已支付，事务 A 提交失败 | 本地仍待支付，后续查单可再次确认 | 本地事务无法回滚已经发生的渠道付款 |
| 事务 A 成功，服务在到账前宕机 | PAID outbox 和补货任务恢复发货 | 不能只在内存里提交一个异步任务 |
| 钱包更新失败、流水或 DELIVERED 写入失败 | 事务 B 整体回滚，订单保持待发货，可重试 | 不能先提交 COMPLETED，再单独给钱包加钱 |
| broker 已收到消息，发送方没收到确认 | 不确认发送完成，允许重投 | 依赖业务幂等，不追求网络层不重复 |
| 钱包到账成功，消费确认丢失 | 重复 PAID 再次走幂等发货，不重复加钱 | “消费失败”不一定代表业务没做成 |
| 钱包已到账，营销 RPC 失败 | DELIVERED 保留未 DONE，重试返利 | 不重复入钱包，不因为赠品暂时失败回滚充值 |
| 营销已受理，RPC 响应丢失 | 同一订单号再调营销，稳定 bizId 返回已有记录 | 跨服务靠业务号关联，不靠临时 MQ 消息 ID |
| 用户付款和超时关单并发 | 先查渠道、渠道关单确认后才本地关；支付先成功则关单条件不成立，关闭先成功则可信支付确认可恢复 | CLOSE 不是不可逆终态，避免把已付款订单永久封死 |
| 积分不足，或扣款事务失败 | 不会扣成负数，流水/task 同时回滚 | 待支付单和 Redis 库存预占已经发生，不随扣款事务回滚 |
| 积分已扣，但 MQ 暂不可用 | task 留下可重试记录；发送成功后消费者增加次数 | HTTP 成功与抽奖次数到账之间存在时间差 |
| 积分扣款成功，HTTP 响应丢失 | 稳定 requestId 找回原订单；相同积分业务号不再扣款 | requestId 当前可选，省略后每次生成新号，重试可能再次购买 |
| 营销消息持续消费失败、进入死信 | 消费异常交给 MQ 重试 | task 已 completed 后不会由 task 扫描重新发送；尚无与充值 outbox 同等级的消费完成闭环 |
| Redis 库存已扣，活动订单尚未落库就宕机 | 同一业务号重试可复用预占 | 用户不再重试时，尚未见自动释放与对账闭环 |

漏回调任务每 15 秒扫描符合条件的订单；超时任务每 60 秒处理超过 30 分钟的订单，具体扫描条件以源码为准。证据：[漏回调查单任务](/Users/tsy/WorkSpace/LLM-market/chatgpt-data/chatgpt-data-trigger/src/main/java/cn/bugstack/chatgpt/data/trigger/job/NoPayNotifyOrderJob.java:11)、[超时关单任务](/Users/tsy/WorkSpace/LLM-market/chatgpt-data/chatgpt-data-trigger/src/main/java/cn/bugstack/chatgpt/data/trigger/job/TimeoutCloseOrderJob.java:11)。

## 5. 已实现与待完善：不要把方案说成已经上线

### 已实现

- 价格/到账额快照，支付通知校验与主动查单。
- 充值支付状态与 PAID 同事务；钱包余额、唯一发放流水、完成状态与 DELIVERED 同事务。
- 充值 outbox 跟踪到消费 DONE；投递确认、重投、退避、消费校验。
- 营销返利订单和 task 同事务，消息发送同步确认。
- 积分业务幂等、数据库余额下限、活动发货 CAS、库存 Lua 防重复扣减。

### 需要优先补齐

**一、积分兑换库存要有可恢复的生命周期。**

当前 Lua 的 reservation TTL 只使预占标记过期，不会自动把库存加回；把 `DECR` 和记预占放在一个 Lua 里，只覆盖 Redis 内的原子性。活动订单创建失败、扣款余额不足都可能留下占用。不能在 catch 里无条件 `INCR`：如果数据库其实已提交、只是响应丢了，释放库存就会制造超卖。

建议以业务号持久化 `RESERVED → CONFIRMED / RELEASED`，按订单与积分流水判定下一步；业务关闭必须与扣款互斥或通过状态条件阻止迟到扣款。释放也要幂等，未知结果先查账。Redis 和数据库之间的变更由可重试事件/任务驱动，并周期核对孤儿预占。

当前数据库库存同步只接受更小的剩余量，是**单调递减快照**。因此补库存释放不能只改 Lua：释放使 Redis 库存增大，现有 SQL 不会同步这个增量，必须同时设计回补流水或带版本的同步协议。证据：[库存预占 Lua](/Users/tsy/WorkSpace/LLM-market/big-market/big-market-app/src/main/resources/lua/activity_stock_reserve.lua:1)、[库存单调快照回写](/Users/tsy/WorkSpace/LLM-market/big-market/big-market-app/src/main/resources/mybatis/mapper/mysql/raffle_activity_sku_mapper.xml:41)。

**二、营销“发送完成”之后，要补业务完成可观测性。**

营销 task 的 `completed` 是 broker 接收确认；扫描只看 `create / fail`，不会感知下游永久失败。建议增加消费处理结果或独立对账任务，关联积分流水、活动订单与返利 bizId，监控“已扣款但长时间未发次数”；死信进入可审计的补发/人工处置流程。同步发送解决发送不确定性，不能代替消费完成确认。证据：[营销同步发送确认](/Users/tsy/WorkSpace/LLM-market/big-market/big-market-infrastructure/src/main/java/com/pro/infrastructure/event/EventPublisher.java:46)、[营销 task 状态与扫描](/Users/tsy/WorkSpace/LLM-market/big-market/big-market-app/src/main/resources/mybatis/mapper/mysql/task_mapper.xml:25)。

**三、启用配置是恢复链路成立的前提。**

`payment.events.rocketmq.enabled` 在基础配置默认 false，prod 配置默认 true，实际可被环境覆盖。关闭时 PAID/DELIVERED 仍可落库，但 relay 和消费者不启动；同步到账和独立补货任务不能自动替代 DELIVERED 返利消费者。面试可说“实现了可靠事件机制”，不能凭源码断言当前部署已经启用。证据：[充值事件功能开关](/Users/tsy/WorkSpace/LLM-market/chatgpt-data/chatgpt-data-app/src/main/resources/application.yml:22)。

**四、补运营对账与可查询的处理中状态。**

建议充值建立“渠道交易 ↔ 订单 ↔ 钱包流水 ↔ 事件”的差异清单；积分建立“订单 ↔ 积分流水 ↔ 次数发放”的差异清单。按积压时长、重复失败次数、死信数量告警，而不是无限重试日志。当前迁移不会自动给历史充值订单回填 outbox，历史差异需核对后修复。

兑换接口目前返回 Boolean，建议返回业务订单号及 `PROCESSING / COMPLETED / FAILED`，支持查询；客户端超时先查原单。强制新客户端传 requestId，并校验同一业务号的金额、SKU 等语义。自动退款、补偿撤销、人工差异处理需要明确业务规则，本次检索的主链路不能证明这些已完整实现。

### 源码审计还发现的两个具体边界

- **分库建表约束不一致。** 仓库的 DB1 积分账户表有 `UNIQUE(user_id)`，DB2 初始脚本没有。若部署沿用该脚本且没有后续修复，Redis 锁失效时不同业务号并发首次建户可能插入重复账户；后续单条查询可能报多行异常，或扣款更新多行后因影响行数不是 1 而回滚，导致交易受阻。不能据此断言线上已经出现重复扣款。建议核对各分库实际 DDL 并统一唯一约束。证据：[DB1 建表](/Users/tsy/WorkSpace/LLM-market/big-market/docs/dev-ops/mysql/sql/big_market_01.sql:682)、[DB2 建表](/Users/tsy/WorkSpace/LLM-market/big-market/docs/dev-ops/mysql/sql/big_market_02.sql:526)。
- **积分消费侧的校验较弱。** 当前只校验负金额、用户和业务号，再查活动订单；没有交叉核验已提交的扣款流水及应付金额。正常生产路径有本地事务保证消息来源，但错误消息若进入 topic，缺少最后一道业务核对。可增加流水金额、交易类型和订单快照校验，并保留异常事件待处理。证据：[CreditAdjustSuccessCustomer](/Users/tsy/WorkSpace/LLM-market/big-market/big-market-trigger/src/main/java/com/pro/trigger/listener/CreditAdjustSuccessCustomer.java:38)。

## 6. 可以直接讲的两分钟版本

> 我把支付拆成支付确认、资产到账、营销返利三个阶段。支付确认以渠道验签和主动查单为准，前端回跳不参与记账。订单会保存支付金额和到账金额快照，避免商品变价影响历史订单。
>
> 确认支付时，我用一个本地事务更新订单并写 PAID 事件；到账时，用另一个本地事务一起完成订单状态变更、唯一钱包流水、钱包加钱和 DELIVERED 事件。这样中途宕机后，数据库里仍然留着下一步要做的事。
>
> MQ 允许重复投递。重复回调、消息和定时补偿都走同一幂等方法，靠条件更新和业务唯一键保证只产生一次资产效果。钱包到账后返利失败，只重试返利，不重复加钱。漏回调通过主动查单恢复，超时关单先确认渠道状态，避免误关已付款订单。
>
> 积分兑换也用了流水、扣款和 task 同事务，收到扣款事件后再增加抽奖次数。但当前实现还有两个边界：库存预占不在 MySQL 事务里，需要补释放和对账；营销 task 只确认消息发送，不代表权益到账，需要补消费完成跟踪。这是我会继续完善的地方。

如果面试官只问 big-market，就从积分兑换图开始，现金充值只作为支付返利的上游背景。

## 7. 追问速答

**为什么不用一个大事务包住 MQ、支付渠道和两个服务？** 外部付款与 broker 投递不受本地数据库事务控制，长事务也不能解决网络结果未知。这里选择持久化业务进度、短本地事务和可幂等重试。当前实现不是 2PC，也不是已具备完整补偿编排的 Saga。

**分库分表为什么还能本地事务？** 积分扣款按 userId 先设置路由，同一用户流水、账户、task 落在同一分库，事务在该数据源内成立；这不意味着跨用户、跨库、跨服务也有同一个事务。

**幂等是不是等于什么都不丢？** 不是。幂等保证重试不会重复生效；持久化任务、调度恢复和对账负责让该发生的事最终发生。两个问题缺一不可。

**为什么不能拿 task completed 给前端显示到账？** 因为它只代表消息送达 broker。需要查询活动订单完成状态或资产发放结果。

**查单超时就退款行不行？** 不行。超时首先是结果未知，先查询原业务和渠道事实；退款是独立业务，需要明确退款单、渠道结果和资产回退规则，不能把异常 catch 当退款流程。
