# 活动 100401：次数奖品迁移为对话余额

## 已确定的业务方向

统一人民币消费余额、后台模型售价表、按实际分类 token 用量计费、每次请求锁定模型和价格版本、预冻结后结算。此变更只补余额奖品的入账基础；聊天 token 扣费、商城充值和旧次数迁移仍需分别实现。

## 迁移约束

- 旧奖品 110–116 使用 `openai_use_count`，不可直接改成金额。2026-10-02 检查发现活动有 17 条历史中奖记录仍处于 `create`，补偿可能继续读取旧奖品配置。
- 新奖品 1110–1116 使用 `openai_balance`，配置单位明确为 CNY，最多 8 位小数。发奖订单作为幂等键，远端入账成功后再完成中奖记录。
- 新策略 10008 保留原概率、库存快照、解锁条件和随机积分奖品 101；历史策略 10007 不覆盖。
- 旧奖品 113 标题是 50 次、配置却是 15；116 标题是 15 次、配置却是 50。新奖品按可见档位纠正：1113 为 50 档、1116 为 15 档。
- 历史中奖记录、已支付订单、用户剩余次数均不批量改写为人民币。积分与人民币余额分账。

## 金额待确定

`prepare-balance-awards.sql` 必须通过同一连接传入已确认的 `@cny_per_legacy_count`，没有默认值。推荐测试值为 `0.01`，对应 0.01 / 0.05 / 0.10 / 0.50 / 0.20 / 0.25 / 0.15 元（转盘顺序）。该建议不是已确认的实际奖励。

## 上线顺序

1. 在 openai 数据库执行独立钱包建表 SQL，部署 `adjust_balance` / `query_account_balance` 接口；部署大市场 `openai_balance` 发奖处理器。
2. 确认兑换比例后执行 `prepare-balance-awards.sql`。脚本只创建新策略，**不会切换活动**。已有目标 ID 时拒绝覆盖，事务异常整体回滚。
3. 完成 token 余额消费入口与余额展示，再切换活动，避免奖励到账后无法使用。
4. 在本地维护窗口阻止新抽奖请求，等待正在执行的请求和库存落库完成；核对新策略库存与旧策略最终剩余量后再装配新策略。不可直接复用较早复制的库存快照。
5. 将活动 100401 从策略 10007 条件更新为 10008，刷新活动缓存，装配新策略。保留旧策略库存、算法缓存及奖品定义供旧订单和补偿使用，不清空 Redis。
6. 核对奖品列表、余额查询、幂等入账和异步发奖完成状态，再恢复活动。

## 本次验证

- 大市场 `OpenAIBalanceAwardTest`：精确金额传递、远端失败不完成中奖记录、非法金额拒绝，3 项通过。
- 临时隔离数据库测试：未设置比例时拒绝执行；生成 8 个奖品；旧次数奖品保留；50 / 15 档位纠正；重复执行拒绝覆盖。临时数据库已删除。
- 尚未将真实活动切换为余额奖品，等待金额决策和消费链路就绪。
